# Pull Request

## Description

This PR delivers one acceptance-criteria item from #1310: enumerate every route that accepts cookie-based authentication for a state-changing operation. The result, documented in `docs/csrf-exposure-audit.md` and enforced by a `cargo test --lib` guard, is that **none do**. #1311, #1312 and #1324 are referenced so that they close with this PR, but nothing from them is implemented here.

**Please read "Separate findings" below.** Enumerating authentication turned up three pre-existing problems, including an unauthenticated admin surface.

## Changes Made

### #1310 Audit CSRF exposure across cookie-based session paths

**Findings:**
- **No route reads or sets a cookie.** Nothing in `src/` touches `Cookie` / `Set-Cookie`, a cookie jar, or `SameSite`, and `security/session.rs` is not bound to a cookie. So no route carries an ambient browser credential, and none is CSRF-exposed that way.
- Two more properties would each block a classic cross-site form post:
  - every state-changing handler takes `Json<_>`, which rejects any content type but JSON (415), and a cross-site JSON request needs a CORS preflight;
  - CORS only allows configured origins.

**Done (AC1):**
- `docs/csrf-exposure-audit.md`: a table of every state-changing route (method, path, middleware, authentication, cookie involvement), the unmounted routers, the separate findings, and what cookie auth must ship with if it's added (credentialed CORS is already configured).
- `src/security/csrf_audit.rs` (`#[cfg(test)]`, 3 tests): fails if any file in `src/` reads or sets a cookie (`header::COOKIE` / `SET_COOKIE`, `"cookie"` / `"set-cookie"`, `CookieJar`, `SameSite`, `tower_cookies`, `axum_extra` cookies), plus positive and negative tests for the scanner.

**Not done in this PR:**
- Per-route SameSite/token/origin protection (AC2). There are no cookie-authenticated routes to protect, and the guard fails CI when one appears.
- Cross-site request tests per route and the 85% coverage target.

### Separate findings (pre-existing, not fixed here)

1. **The admin surface is unauthenticated.** `docs/api-reference.md` says `/admin/*` requires `Authorization: Bearer <ADMIN_API_KEY>`, but `middleware::auth::admin_auth` / `api_key_auth` are not layered on any route, and the handlers extract only `State` / `Path` / `Json`. Affected: `PATCH /admin/transactions/bulk-status`, `PUT /admin/quotas/:tenant_id`, `DELETE /admin/quotas/:tenant_id/reset`, `PATCH /admin/settlements/:id/status`, `POST /admin/reconciliation/run`, `POST /graphql`, `POST /reconnect`.
2. **Webhook signatures are not verified.** `handlers::auth::VerifiedWebhook` (HMAC `X-Stellar-Signature`) has no callers, so `/webhook` accepts any well-formed body.
3. **The CORS config panics at startup** when `CORS_ALLOWED_ORIGINS` is set: `allow_credentials(true)` + `AllowMethods::any()` / `AllowHeaders::any()` trips tower-http 0.4.4's assertion ("Cannot combine `Access-Control-Allow-Credentials: true` with `Access-Control-Allow-Headers: *`"). Reproduced with a throwaway unit test applying the same `CorsLayer` (not committed).
