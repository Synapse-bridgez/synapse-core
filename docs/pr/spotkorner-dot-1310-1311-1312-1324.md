# Pull Request

## Description

This PR delivers one acceptance-criteria item from #1310: enumerate every route that accepts cookie-based authentication for a state-changing operation. The result, documented in `docs/csrf-exposure-audit.md` and enforced by a `cargo test --lib` guard, is that **none do**. #1311, #1312 and #1324 are referenced so that they close with this PR, but nothing from them is implemented here.

**Retargeted to `main`** (from `develop`, which is an ancestor of `main`). An earlier revision of this description, written against `develop`, reported an unauthenticated admin surface and unverified webhook signatures. **Both are already fixed on `main`** (`admin_auth` layered on every admin route, `verify_anchor_signature` on `/webhook` and `/callback`), so those claims are withdrawn. One finding remains; see below.

## Changes Made

### #1310 Audit CSRF exposure across cookie-based session paths

**Findings (on `main` @ `5a770bc`):**
- **No route reads or sets a cookie.** Nothing in `src/` touches `Cookie` / `Set-Cookie`, a cookie jar, or `SameSite`, and `security/session.rs` is not bound to a cookie. So no route carries an ambient browser credential.
- Every state-changing route authenticates with an explicit per-request credential a browser never attaches on its own: `Authorization: Bearer` via `admin_auth` for all admin routes, or the HMAC anchor signature for `/webhook` and `/callback`. A forged cross-site request can't carry either, so none is CSRF-exposed.

**Done (AC1):**
- `docs/csrf-exposure-audit.md`: a table of all 16 state-changing routes on `main` (method, path, authentication, cookie involvement), the unmounted routers, the remaining separate finding, and what cookie auth must ship with if it's added (credentialed CORS is already configured).
- `src/security/csrf_audit.rs` (`#[cfg(test)]`, 3 tests): fails if any file in `src/` reads or sets a cookie (`header::COOKIE` / `SET_COOKIE`, `"cookie"` / `"set-cookie"`, `CookieJar`, `SameSite`, `tower_cookies`, `axum_extra` cookies), plus positive and negative tests for the scanner.

**Not done in this PR:**
- Per-route SameSite/token/origin protection (AC2). There are no cookie-authenticated routes to protect, and the guard fails CI when one appears.
- Cross-site request tests per route and the 85% coverage target.

### Separate finding (pre-existing, not fixed here)

**The CORS config panics at startup** when `CORS_ALLOWED_ORIGINS` is set: `allow_credentials(true)` + `AllowMethods::any()` / `AllowHeaders::any()` trips tower-http 0.4.4's assertion ("Cannot combine `Access-Control-Allow-Credentials: true` with `Access-Control-Allow-Headers: *`"). Still present on `main` (`src/main.rs`). Reproduced with a throwaway unit test applying the same `CorsLayer` (not committed).
