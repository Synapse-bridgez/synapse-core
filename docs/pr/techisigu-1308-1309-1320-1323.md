## Changes Made

### #1323 Security advisory (CVE-style) publishing workflow

**What existed:** `SECURITY.md` covered private *reporting* and triage only. There was no advisory format and no link between a security fix and the SDK/CLI release process.

**Done (AC1):**
- `docs/security/advisory-template.md`: a GitHub Security Advisory template with:
  - affected versions, fixed version (and backports), severity with CVSS v3.1 vector, CWE, and CVE;
  - Impact, Patches (Cargo snippet plus the CHANGELOG `### Security` location), Workarounds (mitigation when an immediate upgrade isn't possible), embargoed Details, Credits, and Timeline.
- `SECURITY.md` → **Publishing Security Advisories**: a before / release / after checklist tied to the existing release tooling:
  - draft GHSA and CVE request, fix in the advisory's private fork, PATCH bump per `VERSIONING.md`;
  - a `### Security` CHANGELOG entry carrying the GHSA ID;
  - a `COMPATIBILITY.toml` entry plus `cargo xtask compat-matrix render` (`cargo xtask release` already refuses versions without an entry, via `compat::ensure_matrix_has_entry_for`);
  - `cargo xtask release`, verify installability, publish the advisory, then expand details after the embargo.
- A disclosure-timing (embargo) policy: nothing identifying the code path before the fix ships; advisory without exploit detail on release day; full details after 14 days (7 for Low) or on active exploitation; a 90-day no-fix fallback.

**Not done in this PR:**
- Actually publishing advisories and cross-referencing existing CHANGELOGs (AC2). No SDK/CLI security fix has been released yet.
- Wiring an optional advisory step into `xtask/src/commands/release.rs`.
- The documented dry-run advisory.
